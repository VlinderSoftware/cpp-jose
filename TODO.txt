    [ ] JWE: per-recipient header is unauthenticated — harden alg selection
        RFC 7516 §7.2 per-recipient "header" members are NOT covered by the
        AAD and can be tampered with undetected.  decrypt() used to read
        "alg" from the per-recipient header to override the protected header's
        kea_ — that algorithm-substitution attack surface is now closed.
        Rules to enforce in decrypt():
        [x] Only accept "alg" from the protected (authenticated) header.
            Per-recipient header "alg" must be IGNORED for key-encryption
            algorithm selection.
        [ ] Per-recipient "header" may only supply non-security-critical hints:
            "kid", "x5t", "x5t#S256", "x5u" — i.e. key-identification
            fields, not algorithm-selection fields.
            Partially done: "alg" and "enc" are now rejected when they
            disagree with the protected header, but the per-recipient header
            is not restricted to a whitelist.  Note that a whitelist of only
            key-identification fields would be too strict: RFC 7518 §4.6
            puts "epk" in the per-recipient header for ECDH-ES, and §4.7 puts
            "iv"/"tag" there for AES-GCM key wrapping.  Both are read from
            the merged effective header by decrypt().
        [x] If a per-recipient header's "alg" is present and DIFFERS from the
            protected header's "alg", return an error at parse time (fromJSON_)
            rather than silently trusting it at decrypt time.
            Also applied to "enc", and to values that are present but not
            strings or not recognised algorithm names.
        [x] Add tests: tampered per-recipient "alg" is rejected; valid
            per-recipient "kid" hint is still honoured.
    [ ] JWE fromJSON: recipients selecting different algorithms (RFC 7516
        §7.2.1 / RFC 7520 §5.13 compliance gap)
        Enforcing "alg" consistency against the protected header means a token
        whose recipients each use a DIFFERENT key-encryption algorithm is
        rejected — including the multiple-recipient example in RFC 7520 §5.13,
        which wraps one CEK under RSA1_5, ECDH-ES+A256KW and A256GCMKW, with a
        protected header of {"enc":"A128CBC-HS256"} that carries no "alg" at
        all.  Multiple recipients sharing one algorithm are supported.
        Deferred because:
        [ ] JWE::Impl holds a single kea_ for the whole token; per-recipient
            algorithm selection needs the algorithm to move onto Recipient.
        [ ] Accepting a per-recipient "alg" means accepting it from an
            unauthenticated source, so it needs a decision on which algorithms
            may be selected that way (an allow-list) before it can be safe.
        [ ] Add test: the RFC 7520 §5.13 vector round-trips and each recipient
            decrypts with its own key.
    [ ] JWE: validate that the encrypting key's intended use is for encryption
    [ ] JWE: validate that is a signing key's public key is used to encrypt a 
        key *to*, the CLI will refuse unless forced
    [ ] JWE: validate we don't encrypt *to* a signing key unless forced
    [ ] JWE fromJSON: absent "protected" header (RFC 7516 §7.2.1 compliance gap)
        RFC 7516 §7.2.1: "protected" MUST be present only when the protected
        header is non-empty; an absent "protected" means an empty protected
        header is in use and alg/enc arrive via the top-level "unprotected"
        (shared) header instead.  The current parser rejects any JSON JWE
        lacking "protected".
        Deferred because:
        [ ] The top-level "unprotected" (shared) header needs to be parsed and
            merged per RFC 7516 §5.2 step 5 before alg/enc can be resolved.
        [ ] Accepting alg/enc from an unauthenticated source requires the
            per-recipient-header hardening item (above) to land first so the
            same security rules apply uniformly to all unprotected header
            locations.
        [ ] Add test: JSON JWE with absent "protected" and alg/enc in
            top-level "unprotected" round-trips correctly.

[ ] Documentation
    [ ] For JWE ECDH-ES, explains OtherInfo according to NIST.SP.800-56A: |
        OtherInfo: A bit string equal to the following concatenation: 
            AlgorithmID || PartyUInfo || PartyVInfo
            {|| SuppPubInfo }{|| SuppPrivInfo } 
        where the subfields are defined as follows:   
        AlgorithmID: A bit string that indicates how the derived keying material 
            will be parsed and for which algorithm(s) the derived secret keying
            material will be used. For example, AlgorithmID might indicate that
            bits 1-80 are to be used as an 80-bit HMAC key and that bits 81-208 
            are to be used as a 128-bit AES key.
            In JOSE, this is the UTF-8 encoded "alg" parameter
        PartyUInfo: A bit string containing public information that is required
            by the application using this KDF to be contributed by party U to 
            the key derivation process. At a minimum, PartyUInfo shall include
            IDU, the identifier of party U. (...))
            In JOSE, this is the contents of the "apu" parameter, which should
            be a unique identifier of the sender.
            Recommend this to be the sender's `kid` of the key used to sign the 
            message (as ECDH-ES does not itself authenticate the sender due to 
            its using an ephemeral key).
        PartyVInfo: A bit string containing public information that is required 
            by the application using this KDF to be contributed by party V to 
            the key derivation process. At a minimum, PartyVInfo shall include 
            IDV, the identifier of party V. See the notes below.
            Recommend this to be the recipient `kid`.
        SuppPubInfo: A bit string containing additional, mutually-known public 
            information. 
            In JOSE, this is the length of the key in bits
        SuppPrivInfo: A bit string containing additional, mutually-known private 
            information (for example, a shared secret symmetric key that has
            been communicated through a separate channel). 
            In JOSE this is not used and empty.
